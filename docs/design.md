# Design: ACME Salary Management

Decisions and their reasons. The one-page requirements are in
[requirements.md](requirements.md), the testable acceptance criteria in
[acceptance-criteria.md](acceptance-criteria.md), and the build order in
[plan.md](plan.md).

The guiding constraint is that this is a one-evening build judged on
judgment, not on size. Where a simpler option answers the product's
questions, it wins.

---

## 1. Architecture

One Node process. It serves the JSON API under `/api` and the built React
app as static files from the same origin.

```
Browser (React, react-router)
        │  fetch, same origin
        ▼
Express  ─ routes      validate input (zod), map errors, no logic
        ─ services     business rules, transactions, the pay rules
        ─ repositories all SQL (Drizzle)
        ▼
SQLite (better-sqlite3)
```

**Why one process rather than a separate API and front end:** same origin
means no CORS, no second deployment to keep in step, and one URL in the
README. At 10,000 rows and a handful of HR users there is nothing to gain
from splitting it.

**Layer rule:** a route never writes SQL; a repository never knows about
HTTP. Services own transactions. The pay rules live in a pure domain
module that touches neither.

### Monorepo layout

```
package.json          npm workspaces: server, web
server/
  src/
    domain/           pure functions, no I/O (pay rules, money, paging)
    db/               drizzle schema, migrations, connection
    repositories/     all SQL
    services/         rules + transactions
    routes/           express, zod, error mapping
    seed/             deterministic 10k seed
web/
  src/
    pages/            one per route
    components/
    api/              fetch helpers
.github/workflows/ci.yml
Dockerfile
```

### Dependencies

Server: `drizzle-orm`, `better-sqlite3`, `express`, `zod`; dev:
`drizzle-kit`, `typescript`, `tsx`, `vitest`, `supertest`, `@types/*`.
Web: `react`, `react-dom`, `react-router-dom`; dev: `vite`,
`@vitejs/plugin-react`, `typescript`. Root: `eslint`, `prettier`.

No date library, no data-fetching library, no UI kit. Dates are ISO
strings handled by `Intl`; money is formatted by `Intl.NumberFormat`.

## 2. Data model

Four reference tables and two data tables. Currency is deliberately **not**
on the employee — it hangs off the country, so a country's statistics can
never mix currencies.

```sql
countries(
  code                TEXT PRIMARY KEY,      -- ISO 3166-1 alpha-2, 'IN'
  name                TEXT NOT NULL,
  currency_code       TEXT NOT NULL,         -- ISO 4217, 'INR'
  currency_minor_unit INTEGER NOT NULL       -- 2 for INR/USD/EUR, 0 for JPY
)

job_titles(id INTEGER PRIMARY KEY, name TEXT NOT NULL UNIQUE)
departments(id INTEGER PRIMARY KEY, name TEXT NOT NULL UNIQUE)

employees(
  id             INTEGER PRIMARY KEY,
  employee_code  TEXT NOT NULL UNIQUE,       -- 'EMP00001'
  full_name      TEXT NOT NULL,
  email          TEXT NOT NULL UNIQUE,
  job_title_id   INTEGER NOT NULL REFERENCES job_titles(id),
  department_id  INTEGER NOT NULL REFERENCES departments(id),
  country_code   TEXT NOT NULL REFERENCES countries(code),
  salary_minor   INTEGER NOT NULL CHECK (salary_minor > 0),
  hire_date      TEXT NOT NULL,              -- ISO yyyy-mm-dd
  status         TEXT NOT NULL CHECK (status IN ('active','left')),
  left_date      TEXT,                       -- set when marked as left
  created_at     TEXT NOT NULL,
  created_by     TEXT NOT NULL,
  updated_at     TEXT NOT NULL,
  updated_by     TEXT NOT NULL
)

salary_changes(
  id               INTEGER PRIMARY KEY,
  employee_id      INTEGER NOT NULL REFERENCES employees(id),
  old_salary_minor INTEGER NOT NULL,
  new_salary_minor INTEGER NOT NULL,
  effective_date   TEXT NOT NULL,            -- defaults to today
  reason           TEXT NOT NULL CHECK (reason IN ('raise','promotion','correction')),
  changed_by       TEXT NOT NULL,
  changed_at       TEXT NOT NULL
)
```

The schema is declared in TypeScript (`server/src/db/schema.ts`) and
migrations are generated by `drizzle-kit`. They run at boot.

**Employee fields** are: employee code (the identifier HR uses, because at
10,000 people names are not unique), full name, email, job title,
department, country, salary, hire date, status and date left. **A salary
change** records the new amount, an effective date that defaults to today,
a reason of raise / promotion / correction, who made it and when.

**Country, job title and department are fixed lists, never free text.**
Free text would split "SDE2" and "SDE 2" into two groups and quietly break
every statistic that groups by job title — including the outlier rule.

### Key trade-off: current salary is denormalised

`employees.salary_minor` holds the current salary, and `salary_changes`
holds the history. The alternative is to derive the current salary from
the newest `salary_changes` row.

| | Denormalised (chosen) | Derived from history |
| --- | --- | --- |
| Aggregates | Plain scan of `employees` over one index | A window or correlated subquery per employee before any aggregate |
| Query to read | Short enough to explain in an interview | Noticeably harder |
| Risk | The two can drift apart | Single source of truth |

Chosen because every statistic in the product is an aggregate over current
salary, and those are the queries that have to stay under 500 ms. The
drift risk is contained: both writes happen in one transaction in the
service layer, and a test asserts the two agree after a change.

### Audit: built in two stages, on purpose

| | Answers | Costs |
| --- | --- | --- |
| **Stage 1 — Must** | What an employee earns and every change to it (old → new, date, reason, who), plus who last touched the record and when | No audit table at all: `salary_changes`, plus `created_at/by`, `updated_at/by` and `left_date` on the employee |
| **Stage 2 — Could** | Which individual fields changed on each edit | A new `audit_events(employee_id, type, summary, details_json, changed_by, changed_at)` table and writes on every mutation |

Stage 1 is columns, not a table. The product promises only stage 1; a full
per-field change history is explicitly a *Could*. If the evening runs
short, "who changed this and when" is still answered.

### Indexes

| Index | Serves |
| --- | --- |
| `employees(country_code, status)` | country overview |
| `employees(job_title_id, country_code, status)` | job overview, outlier groups |
| `employees(status, full_name)` | default list page and sort |
| `employees(status, salary_minor)` | sort by salary |
| `employees(employee_code)`, `employees(email)` | unique lookups |
| `salary_changes(employee_id, effective_date DESC)` | one employee's history |

Name search uses `LIKE '%term%'`, which no index can serve. At 10,000 rows
that is a scan of a single small table and is expected to be a few
milliseconds. It gets measured rather than assumed; if it misses the
budget, the documented next step is an FTS5 virtual table, not a bigger
index.

## 3. Rules the code enforces

- **Money.** Annual gross, stored as a whole number of minor units with
  its ISO currency code. Never a float, never converted between
  currencies, never summed across countries.
- **Outside range.** More than 25% above or below the **median** salary
  for the same job title in the same country. The median rather than the
  average, because the average is dragged by the very outliers the rule is
  meant to find. Groups with fewer than **5** active employees are
  skipped — a group of one sits exactly on its own median.
- **People who have left** are excluded from every statistic, hidden from
  the list until an "include left" toggle is ticked, and read-only. Their
  record and history remain.
- **Who changed it.** There is no login in v1, so the user types their
  name once; it is held for the session and attached to every write.
- **Two people editing at once.** The last save wins. No locking, no
  merge — a small team, and anything else is ceremony here.

The thresholds are not ACME policy, they are this build's choice.
`server/src/domain/payRules.ts` exports `OUTLIER_THRESHOLD_PERCENT = 25`
and `MIN_GROUP_SIZE = 5` plus a pure `isOutsideRange(salaryMinor,
medianMinor, thresholdPercent)`. The SQL in section 4 receives those same
constants as bound parameters, so the pure function and the query cannot
disagree about the rule — and a test pins exactly that.

## 4. The two queries that matter

SQLite has no `median()` and no `PERCENTILE_CONT`. Both queries below run
through Drizzle's `sql` template tag — Drizzle types the plain queries,
but these stay hand-written SQL.

### Median for one group

```sql
WITH g AS (
  SELECT salary_minor,
         ROW_NUMBER() OVER (ORDER BY salary_minor) AS rn,
         COUNT(*)     OVER ()                      AS n
  FROM employees
  WHERE country_code = ? AND job_title_id = ? AND status = 'active'
)
SELECT CAST(ROUND(AVG(salary_minor)) AS INTEGER) AS median_minor
FROM g
WHERE rn IN ((n + 1) / 2, (n + 2) / 2);
```

SQLite's integer division makes the two row numbers collapse to one when
the count is odd and sit either side of the middle when it is even:
n=5 → rows 3 and 3; n=4 → rows 2 and 3. The `AVG` then handles both cases
without a branch. An even-count median can land on half a minor unit, so
it is rounded to the nearest minor unit — recorded here because it is a
real, if small, loss of precision.

### Who is paid outside their range

```sql
WITH ranked AS (
  SELECT id, employee_code, full_name, job_title_id, salary_minor,
         ROW_NUMBER() OVER (PARTITION BY job_title_id ORDER BY salary_minor) AS rn,
         COUNT(*)     OVER (PARTITION BY job_title_id)                       AS n
  FROM employees
  WHERE country_code = ? AND status = 'active'
),
medians AS (
  SELECT job_title_id, n,
         CAST(ROUND(AVG(salary_minor)) AS INTEGER) AS median_minor
  FROM ranked
  WHERE rn IN ((n + 1) / 2, (n + 2) / 2)
  GROUP BY job_title_id, n
)
SELECT r.employee_code, r.full_name, t.name AS job_title,
       r.salary_minor, m.median_minor, m.n
FROM ranked r
JOIN medians m    ON m.job_title_id = r.job_title_id
JOIN job_titles t ON t.id           = r.job_title_id
WHERE m.n >= ?                                  -- minimum group size, 5
  AND (r.salary_minor * 100 > m.median_minor * (100 + ?)      -- +25%
    OR r.salary_minor * 100 < m.median_minor * (100 - ?))     -- -25%
ORDER BY r.salary_minor DESC;
```

The comparison multiplies instead of dividing, so it stays in integers and
never touches a float. `>` and `<` rather than `>=` and `<=` make *exactly*
25% not an outlier, which is the boundary the acceptance criteria name as
a test case.

## 5. API

All responses JSON; all money as integer minor units with its currency.

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/api/reference` | countries, job titles, departments for the dropdowns |
| GET | `/api/employees` | list: `search, country, jobTitleId, departmentId, includeLeft, sort=name\|salary, dir, page, pageSize` |
| GET | `/api/employees/:code` | one employee, including who last changed it and when |
| POST | `/api/employees` | add |
| PATCH | `/api/employees/:code` | edit |
| POST | `/api/employees/:code/leave` | mark as left `{ leftDate }` |
| GET | `/api/employees/:code/salary-history` | dated history, newest first |
| GET | `/api/employees.csv` | export, same filters as the list |
| GET | `/api/insights/country/:code` | headcount, min/max/avg/median |
| GET | `/api/insights/job/:id` | one row per country |
| GET | `/api/insights/discrepancies?country=` | outside-range table |
| GET | `/api/health` | platform health check |

**Money on the wire** is never a float:

```json
{ "amountMinor": 1350000, "currency": "INR", "minorUnit": 2 }
```

The browser formats it with `Intl.NumberFormat`. The server never formats
money and never converts between currencies.

**"Changed by"** travels as an `X-Changed-By` header, required on every
write and validated like any other input. The client holds the name for
the session and attaches it. Keeping it out of the bodies means the create
and update schemas describe the employee only.

**Errors** have one shape everywhere:

```json
{ "error": { "code": "VALIDATION_FAILED",
             "message": "Salary must be a positive whole number.",
             "fields": { "salary": "Must be a positive whole number." } } }
```

Zod failures map into `fields`. Unknown codes never leak a stack trace.

**Paging** returns `{ rows, page, pageSize, total }` so the UI can show
"1–20 of 412" without a second request.

**CSV** is generated by iterating the statement and writing in chunks, so
memory stays flat on a 10,000-row export. It is written with a UTF-8 BOM
and CRLF line endings, because that is what makes Excel open non-ASCII
names correctly — the requirement is "opens in Excel", not "is valid CSV".
Salary is a plain number in its own column with the currency code beside
it, so Excel treats it as a number rather than text.

## 6. Seed data

10,000 employees generated from a **fixed seed**, so every run produces
identical data and the tests and the demo are reproducible. A small
hand-written PRNG rather than a dependency; `Math.random` is never called.

The data is shaped so the product does not look empty:

- roughly 8% marked as having left, with leaving dates
- salary history on a share of employees, one to three changes each
- deliberate outliers inside groups of at least 5 active employees, so the
  discrepancies screen has something real to show
- around 8 countries, 12 job titles, 6 departments, with every
  (country, job title) group that appears holding at least 5 active people

It runs in **one transaction** with prepared statements, and prints its
elapsed time.

**It is guarded: it runs only when the employees table is empty.** Given
the hosting choice in section 9 that means it runs on every cold start —
see the budget in section 8 — and it also means the app stays correct
unchanged if a persistent disk is added later.

## 7. Test strategy

Three layers, all fast and all deterministic. Target: the whole suite in
well under a second, so it can run on every save.

1. **Pure domain tests.** The outlier rule at its boundaries (exactly 25%
   above is not an outlier; 25.01% is), money formatting across minor-unit
   0 and 2, paging arithmetic. No database.
2. **Repository and service tests against `:memory:` SQLite**, seeded with
   about ten hand-written rows chosen to make each case obvious. These
   cover the median SQL for odd and even group sizes, groups below the
   minimum size being skipped, employees who have left being excluded from
   every statistic, and a salary change writing both tables in one
   transaction with `employees.salary_minor` left in step.
3. **A few HTTP tests** (supertest) pinning the contract rather than the
   logic: the error shape, a validation rejection, the paging envelope and
   the CSV header row.

Time is injected through a `Clock` interface so `changed_at` and
"effective date defaults to today" are fixed in tests; the seed uses a
fixed-seed PRNG so there is no randomness; one behaviour per test; test
names read as sentences.

A real `:memory:` database is used rather than a mock because the
product's logic genuinely lives in SQL. Mocking the repository would test
that the mock returns what it was told to.

## 8. Performance

A budget, and a measurement that replaced one:

- **Under 500 ms** for search and list at 10,000 employees, and for each
  insight query.
- **Boot — migrations, reference data and seed:** about 330 ms on a
  developer machine, and **7.6 s measured on the deployed free tier**,
  whose CPU is shared and throttled. That figure is one sample, taken on
  the boot immediately after a deploy. The original 2 second budget was an
  estimate from local timings and is not achievable on that hardware; the
  real number is recorded here rather than the target quietly restated.
  With no persistent disk (section 9) this is paid on every cold start, on
  top of the platform's own container start. The seed is deterministic, so
  the database could instead be built during `docker build` and shipped
  inside the image, making boot near-instant; skipped as over-building for
  a demo. `/api/health` reports the figure, so it stays measured rather
  than assumed.

How they are met:

- Paging, search, filtering and sorting all happen in SQL, 20 rows per
  page. The browser never receives more than a page, except the CSV
  export.
- Every aggregate — count, min, max, average, median — is computed by
  SQLite, never in JavaScript.
- Indexes as listed in section 2.
- `PRAGMA journal_mode = WAL` and `PRAGMA foreign_keys = ON` at startup.
- The seed is one transaction with prepared statements rather than 10,000
  individual inserts.
- `better-sqlite3` is synchronous, which blocks the event loop for the
  duration of a query. At this size, with a handful of HR users and
  millisecond queries, that is the right trade for simplicity and for
  tests that need no async plumbing. If this had to serve thousands of
  concurrent users the answer would be a client-server database, not a
  worker thread — recorded so the choice is visibly a choice.

Measured rather than assumed: seed time and the timings for the list and
each insight endpoint go in the README's performance notes.

## 9. Deployment

Single container. Multi-stage Dockerfile: build `web` with Vite, build
`server` with `tsc`, copy both into a slim runtime image. Express serves
`web/dist` for anything that is not `/api`, and reads `PORT` from the
environment, so the container is host-agnostic and the host stays a late,
cheap decision.

**No persistent disk.** The SQLite file lives on the container's own
filesystem at `DATABASE_PATH` (default `./data/acme.db`). Boot order is
migrate → seed if empty → listen, so the app never serves a half-built
database.

### The trade-off, stated plainly

- **Data resets on every redeploy and every restart.** Anything the HR
  manager adds or edits is lost when the container is replaced. The app is
  never *empty* — the deterministic seed rebuilds the same 10,000
  employees — but edits are not durable.
- **The first load after the host sleeps is slow.** Free hosting tiers
  stop an idle container; the next request pays container start plus
  migrations plus the seed — measured at 7.6 s on this tier, see section 8.

This is acceptable for v1 because there is no login and no real salary
data in it: it is a demo over reproducible fixtures, not a system of
record. It would not be acceptable the moment either of those changed, and
"add a volume" is the first item on the list below.

### Upgrade path

Mounting a disk and pointing `DATABASE_PATH` at it makes the data durable
with no code change — the seed's empty-check guard is already written so
that it does the right thing when the database survives a restart. The
guard is not wasted work; it is what makes the upgrade a configuration
change.

Chosen over a volume-backed deployment because every provider offering a
mounted disk wanted card details up front, and that is not a trade worth
making for an assessment demo.

## 10. What this design deliberately leaves out

- **No caching layer.** Queries are milliseconds; a cache would add
  invalidation bugs and nothing else.
- **No background jobs, no queue.** Nothing here is slow enough to defer.
- **No generic audit framework.** See section 2.
- **No DTO mapping layer.** Repositories return rows shaped for their one
  caller; a mapping layer at this size is ceremony.
- **No authentication.** Out of scope, and it would be the first thing
  added next — along with the disk.
